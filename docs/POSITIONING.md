# 产品定位

> 本文回答四个问题：**卖给谁、不卖给谁、和 Docker 的分界在哪、和竞品比赢在哪输在哪。**
> 每一条能力声明都对应一次真实调用；本文引用的数字来自一次可复跑的演练，
> 复现方法见文末。

---

## 1. 一句话

**单机、自托管、容器档隔离、多租户的 Agent 代码执行底座。**

拆开来看这四个限定词都不是修饰，而是**排除**：

| 限定 | 排除掉的场景 |
|---|---|
| 单机 | 需要跨节点调度、异地多活的场景 |
| 自托管 | 想直接用云 API、不想运维场景 |
| 容器档 | 直接执行不可信第三方代码的场景 |
| 多租户 | 单用户本地开发工具 |

一句话说清它的价值：**把「多租户治理」和「容器运行时」装进一个零依赖的二进制，
并且把隔离档的真实边界写在可以程序化核对的地方，而不是写在 README 的形容词里。**

## 2. 客户画像

### 该买

- **企业内部 AI 编程助手**：Agent 生成代码 → 在受控环境里构建/测试。代码来源是
  自己的 Agent（受信任或半受信任），不是外部用户提交的。
- **数据主权/合规受限**：代码与产物不能出机房，因此不能用云端沙箱服务；
  又不想为几十个开发者维护一套 Kubernetes。
- **需要按业务线隔离与计量**：多个团队共用一个平台，各自要有独立的 Key、
  配额、速率和审计记录。
- **需要「装好依赖的环境」秒级复用**：不想每次跑任务都重装依赖。

### 不该买

- **直接执行外部用户提交的代码**（在线判题、SaaS 代码解释器）。这需要 microVM 级隔离。
- **需要 GPU 的推理/训练沙箱**。不支持。
- **需要云端弹性伸缩到数千并发**。单机，且没有多节点。
- **需要开箱即用的 Python/TS SDK**。只有 HTTP API 与 `sbxctl` CLI。

## 3. 威胁模型边界（买之前必须接受的四件事）

1. **沙箱与宿主共享内核。** 容器档隔离，逃逸需要同时击穿
   namespace + dropped capabilities + seccomp + no-new-privs + 只读路径屏蔽。
   正确的说法是"同时击穿每一层"，**不是**"无法逃逸"。
   这个边界可程序化核对：`GET /readyz` 的 `.isolation`，`GET /v1/isolation` 的完整证据。
2. **身份不分离（当 `userns=off` 时）。** 沙箱内的 uid 0 就是宿主的 uid 0。
   一旦有内核提权漏洞，不需要第二次提权。`userns = require` 能让不具备
   user namespace 的宿主**拒绝启动**，而不是静默降级。
3. **两条控制无法强制，因此被拒绝而不是假装。** 磁盘配额（overlayfs 无法强制）
   与 egress 白名单（容器后端无法强制）都返回 **501**，并给出可执行的替代说明。
   这是产品设计，不是缺陷——见第 5 节。
4. **执行隔离 ≠ Agent 隔离。** pi 扩展只把 `bash`（命令执行）路由进沙箱；
   `read/write/edit/ls/grep/find` 六个文件工具、pi 进程、LLM 凭据都仍在宿主机。
   所以它防"模型生成的代码作恶"，**不**防"Agent 本身不可信"。要 Agent 级隔离，
   正解是把整个 pi 进程跑进沙箱（`docs/RESEARCH.md` §2.5 第二模式），而不是靠本扩展。

## 4. 与 Docker 的分界

Docker 是**运行时**：它负责把容器跑起来。本项目是运行时**之上的多租户控制面**。

| | Docker Engine | Sandcastle |
|---|---|---|
| 租户身份 | 无此概念 | Key + scope（admin/tenant），存 SHA-256 哈希 |
| 配额 | 无 | 每租户并发沙箱/CPU/内存上限 |
| 限流 | 无 | 每租户 × 操作组（create/exec/files/snapshot/read）令牌桶 |
| 审计 | 无 | 每个状态变更一条事件 |
| 调用面 | `docker` CLI / API | HTTP REST，供 Agent 直接调用 |
| 环境复用 | `docker commit`（需自己管理） | 快照 + 引用计数 + 孤儿镜像回收 |
| 生命周期 | 需自己写 | 建/停/删/暂停/恢复/空闲超时/TTL/透明恢复 |
| 崩溃一致性 | 需自己写 | WAL + fsync + 重启后 reconciler 重建真相 |

关键区别不是"更安全"，而是**"有人在管"**：`docker run` 不区分谁在跑、
跑了多少、该不该拒绝、事后谁查得到。

## 5. 为什么用 Docker Engine

原因是分层的，从前提到实现：

1. **目标档位就是容器档。** 既然不追求 microVM，就没有理由自己实现
   namespace/cgroup/OCI 规范——那是几万行别人已经调好的代码。
2. **复用整个容器生态。** 任意 OCI 镜像、registry、overlayfs、cgroups、
   seccomp、AppArmor、user namespace 全部直接继承。
3. **它是 API 客户端，不是 CLI 包装。** 生产代码通过 `/var/run/docker.sock`
   上的 HTTP 与引擎通信，**从不 `exec.Command("docker", ...)`**——
   在 `cmd/` 与 `internal/` 下 grep 该模式零命中。这既堵死了命令行注入，
   也让"零第三方依赖"成立（客户端是标准库写的）。
4. **它是一个刻意留出的替换缝。** `HostConfig.Runtime` 未写死，因此宿主把
   `default-runtime` 换成 Kata / Sysbox / gVisor 就能零代码改动升到 VM 级隔离。
   同时 `internal/runtime` 定义了 `Backend` 接口，`fc` 包是编译通过的第二实现
   （骨架），保证接口演进不会只为一种后端设计。

## 6. 竞争格局（2026-10）

| 层 | 代表 | 隔离 | 部署 |
|---|---|---|---|
| 托管 microVM | E2B、Blaxel、Vercel Sandbox、Cloudflare、CodeSandbox(Together)、Runloop、AWS/Google | Firecracker / gVisor | 仅托管（部分 BYOC） |
| 容器默认 + VM 可选 | **Daytona** | 容器（Kata/Sysbox 可选） | 2026-06 起仅 BYOC |
| 自托管重量级 | Northflank、agent-sandbox(K8s)、boxxkite、OpenSandbox | Kata/gVisor/microVM | 需要 Kubernetes |
| 自托管单二进制 | **hermesx**、vivek1504/serverless-runtime、**Sandcastle** | 容器 / Firecracker | 单二进制 |

隔离强度排序在两年内没有变过：**Firecracker / Kata ≥ gVisor > 普通容器**。

### 最有力的证据来自对手退场

Daytona 是与本项目**架构最接近**的同类——同样默认容器档、把 Kata/Sysbox 作为可选强化，
融资 3100 万美元。2026 年 6 月它把核心开发移入私有仓库，**2026-10-03 归档了公开仓库**
（AGPL-3.0，冻结在 v0.190.0），官网删除了自托管文档。官方给出的理由是
**"AI 辅助的漏洞挖掘正在针对公开的隔离代码"**。

这句话本身就是容器档定位的注脚：一个架构选择与本项目重合的公司，因为同一档隔离的
**实现细节**经不起公开而选择了关灯。本项目的回答不是把实现藏起来，而是把**契约**公开：
哪些是实测的、哪些明确不承诺、怎么自己核对。

## 7. 赢在哪，输在哪

### 优势（可核对）

| 优势 | 证据 |
|---|---|
| **零第三方依赖的单二进制** | `go.mod` 只有 `module` 与 `go 1.26` 两行；生产不 exec docker |
| **治理在进程内强制** | Key/配额/限流/审计全部内建，不需要 Redis/Postgres/K8s |
| **可证伪的安全姿态** | `/readyz` 报隔离档、`/v1/isolation` 报内核事实、`SECURITY-CONTRACT.md` 有"明确不承诺"一节 |
| **环境复用闭环** | 快照 → 从快照冷启 → 读回原沙箱产物（可证伪：该文件不存在于基础镜像） |
| **崩溃后自愈** | `kill -9` 后重启，reconciler 从后端重新推导状态 |

### 劣势（同样明确）

| 劣势 | 说明 |
|---|---|
| 隔离弱一档 | 共享内核；E2B/CodeSandbox/Blaxel 的 Firecracker 更强 |
| 无 SDK | 只有 HTTP + CLI；竞品普遍有 Python/TS SDK |
| 单机 | 无多节点、无 HA、无选主 |
| 无 GPU | 竞品普遍有 |
| 无 SDK / 无 PTY 流式 | 同步 exec 已可用；PTY 在路线图 |

计量计费与冷启动数字在 v1.1.6 由「无」转为「有、且可复现」：`GET /v1/metering`
提供 vCPU/GiB/会话小时的采样积分计量（`docs/API.md`「计量」），`make bench` 一键
产出冷启动/吞吐数字（`docs/bench-summary.json`）。二者口径见 `docs/ROADMAP.md`
P0-1 / P0-2，这里不再把它们列为劣势。

## 8. 场景实测（本节所有数字来自一次真实演练）

**场景：多业务线 AI 编程助手的代码执行底座**
（平台接入与合规取证 → Agent 建沙箱/传代码/执行/取产物 → 快照复用 →
暂停回收与透明恢复 → 治理边界 → 审计与回收 → 崩溃恢复）

| 指标 | 实测值 |
|---|---|
| 真实调用 | 47 次 |
| 断言 | 43 / 43 通过 |
| 响应分布 | 200×23、201×9、204×4、401×1、402×1、403×3、409×3、429×1、501×2 |
| 隔离档 | `container-shared-kernel`，自检已执行，`userns=off` |
| 隔离证据 | 10 项事实，其中 9 项被断言，失败 0 项 |
| 调用耗时中位 | 7 ms |
| 建沙箱 | 163 ms |
| 创建快照 | 137 ms |
| 从快照建沙箱 | 160 ms |
| exec | 26 ms |
| 审计事件 | 24 条 |

**四个关键的可证伪断言：**

1. **快照复用是真的**：沙箱 1 里写入的 `result.txt`（基础镜像中不存在），
   在从未构建镜像的沙箱 2 中被读回，内容 `3`。
2. **透明恢复是真的**：对 `paused` 沙箱直接 exec 返回 `resumed-by-auto_resume`，
   调用方无需先 resume。
3. **限流是真的**：租户 B 的 create 桶设为 `0.05/s burst 1`，连发第二次返回
   `429` 且带 `Retry-After: 20`。
4. **配额是真的**：租户 A 已有 1 个沙箱、上限压到 1 后，下一次创建返回
   `402 quota_exceeded`——**不是** 429。"稍后重试"与"买更多容量"是不同指令。

**同样重要的：本场景没有证明什么。**
没有证明隔离强度（那是 `/v1/isolation` 的事，且只覆盖已断言的那几项）；
没有证明高并发下的表现（单机顺序调用）；没有证明多节点行为（不存在）。

冷启动与吞吐**单独由 `make bench` 测量**（不并入本场景，因为它的方法论不同——
只测量不设硬断言，见 `docs/ROADMAP.md` P0-2）。参考数字（2026-10-11，macOS /
Docker 29.5.2，随机器负载浮动，非承诺）：冷启动到 ready 约 7.7s（被隔离自检这个
I/O 密集步骤主导）、exec p50 ~24.6ms / p99 ~35.5ms、建沙箱 p50 ~184ms / p99 ~196ms、
80 并发建沙箱 ~4.6s 全部准入。完整原始值见 `docs/bench-summary.json`。

## 9. 本次演练顺带确认的三个边界与缺口

1. **`disk_mib` 与 egress 白名单返回 501，不是 400。** 语义是"本节点不具备该能力"，
   而非"请求格式错误"。客户端应据此区分重试与降级。
2. **平台默认速率硬编码（已知缺口）。** 管理面 bucket 是 `1/s burst 5`，
   `sandboxd.conf` 没有对应键；演练中连续的管理面调用确实收到过 429。
   全平台调整需要对每个租户逐个下发 `quota.rates`。
3. **`PATCH /v1/tenants` 是整对象替换，不是合并（已知缺口）。** `updateTenant`
   执行 `t.Quota = *body.Quota`，因此只带 `max_sandboxes` 的 PATCH 会把该租户的
   自定义 `rates` 一并抹掉、静默回退到平台默认。本次演练**已复现**：一次遗漏
   `rates` 的配额修改导致后续创建意外 429。修法是每次配额写入都带全 `rates`
   （演练脚本已如此处理），但语义本身值得商榷。
